# 前台与后台 UI 代码评估

日期：2026-10-11。目标：本地 localhost:8080 的 amaze 前台与墨韵后台。

结论：设计系统和服务端模板拆分合理，适合个人博客继续迭代。前台公共脚本较轻，后台主要问题是旧页面脚本的状态管理、校验和插件调用没有随主题改造一起整理。应先修复逻辑问题，再优化重复代码与资源加载。

本次通过浏览器查看实际页面、打开分类编辑弹窗、运行项目实际评论校验函数，并对照模板、脚本与控制器。后台登录由用户完成。没有保存、发布、删除、上传或修改配置。打开文章详情会按应用原有逻辑增加浏览量。

## 已确认的问题与优先级

### 1. 分类表单状态混用，编辑没有回填（优先）

- 界面复现：选择“日常随笔”，点击修改，分类名称为空，图标选中默认图标。
- `category.js:120` 的 `categoryEdit()` 先 reset，只赋值 categoryId，没有读取分类原来的名称和图标。
- `category.js:87` 保存时依据表格当前是否选中行来判断新增或更新，而不是依据当前弹窗模式。
- `category.js:168` 的 reset 没有清空 categoryId，也没有清理错误提示或完整同步图标选择插件。
- 因此，表格选中一行后点“新增分类”仍可能走 update；在已编辑过的情况下还可能携带旧 ID。这个请求分支通过代码确认，没有实际提交更新验证，避免改动数据。
- 建议：显式区分 create/edit 模式；编辑时回填现有数据；新增时清空 ID、字段、错误与插件选中状态；保存请求只由弹窗模式和 ID 决定。

### 2. 分类初始化调用不存在的插件方法（优先）

浏览器控制台实际捕获：`TypeError: container.imagesLoaded is not a function`，位置 `category.js:50`。当前模板没有 `.image-picker.masonry`，脚本仍无条件调用 imagesLoaded。即使容器为空，也会因方法不存在而报错。

建议删除当前页面不需要的 masonry 初始化；如果未来需要，按页面加载依赖，并检查容器和方法后初始化。不要仅为了消除错误继续增加无用依赖。

### 3. 前台评论校验拒绝正常表达，前后端规则不一致（优先）

项目实际 `blog/plugins/comment/valid.js:34` 函数验证结果：

| 输入 | 前端结果 |
| --- | --- |
| 写得很好 | 通过 |
| 写得很好！ | 拒绝 |
| 请问怎么配置？ | 拒绝 |
| 第一行 + 换行 + 第二行 | 拒绝 |
| 150 个 a | 拒绝 |

`comment.js:38` 把“名称”字符白名单用于正文，只允许少量字符且限制 2–100 字。控制器 `MyBlogController.java:251` 对正文的规则是非空、最多 200 字。后台回复 `admin/dist/js/comment.js` 也复用了同类名称校验。

建议：称呼与正文分开校验，正文允许正常标点和换行；统一前后端长度规则，界面注明限制。错误提示应定位到字段，保留输入。正文显示已经使用 th:text，这一转义方式应保留。

### 4. 配置保存按钮禁用后不恢复（优先）

`configuration.js:4、33、61` 点击时设置 disabled=true，但 success、error 或 complete 都没有恢复按钮。成功之后不能继续保存，失败之后也不能直接重试。

这是代码确认的问题。本次只查看配置表单，没有点击保存来改变持久化数据。

建议：请求期间显示“保存中”，在 complete/finally 恢复按钮；失败时保留字段并说明可重试。

### 5. 文章正文长度校验用错变量（优先）

`edit.js:132` 使用 `validLength(blogTags, 100000)` 检查“文章内容过长”。标签已经在前面通过 150 字限制，因此这次校验基本失去意义。

建议改为正文变量，并明确是否需要 trim；公共 validLength 当前使用 `<`，会拒绝恰好等于上限的长度，应统一为明确的最大长度语义。

### 6. 手机端表格布局不可读（较高）

实际后台文章页在手机宽度下，将标题、预览图、阅读量、状态、分类、时间压缩到同一张表里。DOM 测量：视口宽 382px，表格可视宽 298px，表格内容宽 298px，overflow-x 为 hidden。这里主要是列被压缩，并非已证实的横向内容溢出。

建议：小屏只保留标题、状态和操作，其他信息放进详情；或给表格合理的最小宽度并允许横向滚动。桌面表格封面目前固定 160×120，表格高 700px，四条记录也占据很长页面；缩小封面并采用自动高度会提高浏览效率。

### 7. 请求结果、失败和空状态需要统一（中等）

- `dashboard.js:35–40` 把非 200 的业务结果也归到“暂无内容”，容易把失败当成真实空列表。
- 多个列表批量操作只有 success，没有对应的网络失败处理。
- 编辑与评论提交没有请求期间的禁用/进行中状态，存在重复触发请求的可能；本次没有提交数据来验证是否产生重复记录。
- 部分业务失败分支关闭弹窗，迫使用户重新打开才能修正。

建议：提取小型请求封装，统一业务错误、网络错误、登录失效和按钮恢复。保持 loading / empty / error / success 四种状态，错误时提供重试。

### 8. 写作流程保护不足（中等）

`edit.js` 未发现离开前提醒或草稿恢复。新文章的发布状态默认选中，顶部按钮叫“保存文章”，最后弹窗按钮叫“确认”，结果不够直观。

建议优先加入未保存提醒与本地草稿恢复；把“保存草稿”和“发布文章”明确区分，并根据最终结果设置按钮文案。不要把未保存内容提示与每次普通导航混在一起。

## 代码结构的优点与后续优化

- 前台 `layout.html`、post-card、sidebar、pagination 等片段已有复用，服务端输出负责列表和分页，公共 JS 只补充导航、搜索与回到顶部，职责较清楚。
- 前台已使用 defer、图片 lazy loading、focus-visible、skip-link、移动菜单 aria-expanded 与 reduced-motion，这是好的基础。
- 前后台共享 tokens，后台额外补充尺寸和状态色，样式按 base/layout/components/plugins/pages 分层。建议继续保留这套结构。
- dashboard 动态插入访客评论和文章标题采用 `.text()`，避免把正文内容直接当 HTML 插入，值得保持。
- 无需为当前规模立即换框架。先把各列表重复的 jqGrid 初始化、分页映射、resize、reload、确认对话框收敛到小型公共模块，页面保留列定义和业务行为。
- 公共入口 CSS 当前通过 @import 加载多个文件。开发中保留分文件，部署时合并/压缩成入口资源，有助于减少入口发现后的额外样式请求；本次没有做网络性能采样，不能给出速度提升百分比。
- 编辑保存成功弹窗仍混用 type、confirmButtonText 等旧选项，而当前加载的 SweetAlert 实现将这些列为 deprecated。统一现有弹窗 API 和主题配置，减少旧选项警告与默认英文按钮。没有触发保存成功流程，未将其作为现场复现问题。
- 前台评论和后台编辑会 console.log 整个表单对象；正式使用时移除这些调试日志，尤其是邮箱、评论和文章全文。
- 后台侧栏抽屉仅有 class 切换与遮罩关闭，建议增加 aria-expanded、Esc 关闭、焦点恢复与打开时的背景交互限制。前台已有 aria-expanded，后台可以沿用同样的状态同步方式。

## 证据边界

本次是 UI 与代码逻辑评估，不是完整安全审计或性能基准。截图不能证明完整无障碍合规。未覆盖保存/删除/上传的真实写入、断网/超时/会话失效、多页分页、读屏和所有键盘路径。前台截图是桌面证据，手机现场截图来自后台。现有源码、数据库内容和配置未修改；仅新增本报告与检查截图。

建议顺序：分类状态与插件错误 → 评论与正文校验 → 保存状态与防重复提交 → 手机表格 → 草稿保护 → 复用与资源优化。
